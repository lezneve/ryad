# ryad / технічний аналіз і архітектура

назва: **ryad** («ряд»). у коді живе в одній константі `APP_NAME` (`src/main.rs`).

стан на 2026-11-14: етапи 1–7 пройдено в обсязі 0.1 на windows 11 (одна машина, один дисплей 150 %); windows 10, інші масштаби, ime, екранний диктор і реальні клавіші з модифікаторами не перевірені. що перевірено і як — [testing.md](testing.md), цифри — [measurements.md](measurements.md).

---

## 0. продуктовий контракт

**що це:** нативний редактор чернеток і звичайних текстових файлів для windows 10/11 x64. закриває щоденні сценарії з notepad++: записати щось і повернутися завтра; відкрити лог із провідника, увімкнути перенос, знайти, скопіювати, зберегти.

**контракт відновлення:** після повного закриття (×, alt+f4, кінець сеансу windows) ryad повертає всі вкладки в тому самому порядку, активну вкладку, текст, курсор, виділення, прокрутку і перенос. незбережені правки файлів повертаються як локальна копія, файл на диску лишається на останній збереженій версії. після примусового завершення повертається останній підтверджений запис сесії; правки після нього можуть бути втрачені.

**що змінює файл користувача:** тільки `ctrl+s`, «save as» і явний вибір у діалозі конфлікту.

**поза 0.1:** підсвітка синтаксису, дерево проєкту, markdown-preview, мультикурсор, regex, плагіни, синхронізація, автооновлення.

**бюджети:** baseline виміряно (measurements.md). числові цілі — рішення команди.

### що не взято і чому

- **direct2d/directwrite для власних поверхонь.** у kadr вікно налаштувань живе в окремому короткому процесі, бо directwrite лишав у процесі 5–8 мб після використання (kadr measurements.md). вікно ryad відкрите весь час, тому вкладки, статус, номери рядків і панелі малюються gdi: плоскі заливки, лінія в 1 px, текст через `DrawTextW`.
- **трей, гарячі клавіші, overlay, захоплення** — у редакторі нема відповідного сценарію.
- **крапкові мітки обрізу** (знак kadr) — знак ryad інший: смужка-«чорнило» над активною вкладкою.
- **вікно інсталятора kadr і його direct2d-полотно** взято майже без змін (`installer.rs`, `canvas.rs`): інсталятор живе у власному короткому процесі, тому directwrite не потрапляє в процес редактора.

## 2. життєвий цикл і процеси

```text
старт ──> маніфест: per-monitor-v2, common controls 6
     ──> аргументи; відносні шляхи стають абсолютними тут, у теці виклику
     ──> ipc::claim: mutex Local\ryad.<hash каталогу даних>
           перший  → власник: ексклюзивний session\lock, далі app::run
           другий  → WM_COPYDATA зі шляхами у вікно власника, вихід
     ──> OleInitialize (drag and drop rich edit, системні діалоги)
     ──> вікно з остаточним розміром → відновлення сесії → файли з командного рядка
     ──> GetMessage: спить, поки немає повідомлень. таймер є тільки після
         правки (запис сесії) і зникає після запису
вихід ──> останній запис сесії, очікування писальника; помилка → діалог
          «повторити / зберегти як / вийти без останніх змін»
     ──> settings.ini, знищення вікна, писальник завершується (join), процес виходить
```

потоки: ui-потік (вікна, контроли, живий текст) і потік писальника сесії. файли користувача читаються й пишуться в ui-потоці синхронно; час — у measurements.md.

## 3. текстове поле

### критерії вибору (етап 1)

1. **вірність тексту:** що прочитали, те й показали, скопіювали й зберегли — кирилиця, emoji, комбіновані знаки, crlf/lf/cr, відсутній фінальний перенос.
2. **перенос як відображення:** перемикання не змінює текст, виділення, undo і прапорець змін.
3. **undo/redo на вкладку**, що живе під час перемикання вкладок; «замінити все» скасовується за один крок.
4. **ввід windows як є:** ime, розкладки, буфер обміну, drag and drop, клавіатурна навігація, екранний диктор.
5. **розмір і швидкість:** багато коротких рядків і один дуже довгий, 1/10/50 мб.
6. **пам'ять** на вкладку з undo і звільнення після закриття.
7. **ціна:** залежності, розмір exe, обсяг власного коду. власне поле означає власні введення, виділення, буфер, юнікод, undo і доступність.

кандидати: `EDIT` (comctl), rich edit 4.1+ (`msftedit.dll`, клас `RICHEDIT50W`) у режимі plain text, власне поле (directwrite + tsf). `EDIT` відпав без прототипу: undo тільки на один крок, а перенос задається стилем при створенні, тобто перемикання переносу — це нове вікно і втрачений undo.

### spike: rich edit у plain text

`research/spikes/richedit` (сирі таблиці там же). режим: `EM_SETTEXTMODE(TM_PLAINTEXT | TM_MULTILEVELUNDO | TM_MULTICODEPAGE)`, текст через `EM_SETTEXTEX` / `EM_GETTEXTEX` у utf-16, ліміт `EM_EXLIMITTEXT`.

| перевірка | результат | висновок для ryad |
|---|---|---|
| crlf, lf, lone cr, фінальний перенос | кожен перенос у контролі стає одним `\r` | кінці рядків запам'ятовує ryad; у контролі завжди `\r` |
| `\r\r\n` | **обидва символи зникають** (`a\r\r\nb` → `ab`) | не віддавати контролю сирі кінці рядків: `files::to_control` перетворює кожен crlf / lf / cr на `\r` до завантаження |
| nul | текст обрізається на нулі | файл з нулями — «схожий на бінарний», не відкривається |
| u+2028 / u+2029 | стають vt / `\r` | файл з ними не відкривається з поясненням: контроль змінив би текст |
| vt, ff, tab, emoji з zwj, прапор, комбіновані знаки, кирилиця | без змін | ✔ |
| позиції | utf-16 code units, перенос рядка = 1 unit; позиція всередині surrogate pair зсувається на початок пари | одиниці контролю = utf-16 тексту з `\r`, конвертація тільки на межі `editor.rs` |
| перенос (`EM_SETTARGETDEVICE` 0/1) | текст, виділення, прапорець змін, undo (30 кроків) і redo без змін; 6–10 мс на 200 рядках | ✔ перенос — суто відображення |
| «замінити все» через `EM_SETTEXTEX(ST_KEEPUNDO \| ST_SELECTION)` | один крок undo | ✔ |
| `WM_CHAR` кирилиці й surrogate pair | вставляються як є | ✔ (ime — тільки вручну, testing.md) |
| ліміт за замовчуванням | 100k символів через `EM_SETTEXTEX` і через вставлення пройшли | все одно `EM_EXLIMITTEXT(0x7ffffffe)` |
| пам'ять: 5 вкладок × 1 мб тексту | +14–17 мб private, 200 правок з undo на вкладку — ще +2–3 мб; після знищення повертається більша частина (купа процесу лишає 2–3 мб) | одна вкладка = один контрол, undo живе в ньому |
| 1 / 10 / 50 мб коротких рядків | 0.09 / 0.86 / 4.3 с на завантаження, лінійно | межа файла 64 мб, перевірка розміру до читання |
| один рядок 1 мб (латиниця з кирилицею) | **5.2 с**, 10 мб — **564 с** | причина нижче |
| `EM_GETLINECOUNT` | змушує перерахувати весь макет: ~1 с на 10 мб | не використовується; кількість рядків рахує ryad |
| логічний рядок (абзац) через tom `ITextRange::GetIndex(tomParagraph)` | 2 / 27 / 114 мс у кінці 1 / 10 / 50 мб з переносом | номери рядків з кешем (розділ 5) |

**причина повільного «довгого рядка».** не довжина рядка: той самий мегабайт, розбитий на рядки по 1000 символів, теж вантажився 5.8 с, а чиста латиниця — 0.13 с. винен `IMF_AUTOFONT` (`EM_SETLANGOPTIONS`): на кожній межі латиниці й кирилиці rich edit підбирає шрифт і робить новий відрізок формату. без `IMF_AUTOFONT` — 0.09–0.12 с на мегабайт, лінійно до 50 мб. але без нього немає заміни шрифту для символів, яких бракує в cascadia mono, і emoji стають квадратиками.

**рішення:** текст до 128k символів завантажується з `IMF_AUTOFONT` (емодзі видно; для звичайного тексту це десятки мілісекунд), більший — без нього, після чого `IMF_AUTOFONT` вмикається знову для нового вводу. у великих файлах emoji з самого файла показуються квадратиками, сам текст не змінюється (обмеження в readme).

**також з'ясовано:**
- rich edit перераховує макет усього тексту при кожній зміні розміру вікна. тому вікно отримує остаточний розмір до завантаження тексту, новий контрол народжується у своєму прямокутнику, а `move_if_needed` не чіпає вікно з тим самим прямокутником. відкриття 10 мб: «готовий до вводу» з 2.8 с до 0.84 с.
- рядок у 10 мб без переносу вантажиться 3.9 с, з переносом — 0.78 с. файл, у якому є рядок довший за 20 000 байт, відкривається з увімкненим переносом (alt+z вимикає).
- color emoji в rich edit є тільки в режимі d2d (`RichEditD2DPT`), а системний `msftedit.dll` 10.0.26100 цього класу не реєструє. emoji монохромні.
- у plain text режимі форматні скорочення rich edit (ctrl+b/i/u/l/e/r/1/2/5, ctrl+shift+a…) форматували б увесь текст, а ctrl+літера вставляє керівні символи. subclass контролу (`editor::subclass`) пропускає тільки навігацію, буфер обміну й undo; клавіші ryad приходять раніше через таблицю акселераторів.

**рішення: системний rich edit.** він проходить ключові сценарії: перенос без втрат, undo на вкладку, ввід і буфер обміну windows, доступність контролу — за ціну двох обходів (нормалізація кінців рядків до завантаження, `IMF_AUTOFONT` за розміром) і без нових залежностей. власне поле не потрібне.

## 5. модель документа

вкладка має стабільний `id`. шлях з'являється після «save as» і може змінюватися без заміни вкладки.

| ревізія | що означає |
|---|---|
| `rev` | живий текст, +1 на кожну зміну (`EN_CHANGE`) |
| `saved_rev` | ревізія, текст якої лежить у файлі користувача (для нової чернетки — порожній початок) |
| `snap_rev` / `snap_name` | ревізія, копію якої тримає підтверджена сесія |

крапка на вкладці: `rev != saved_rev`. після автозапису крапка лишається, доки файл не збереже той самий текст. для документів до 2 млн символів кожна зміна з тією ж довжиною, що й збережений текст, порівнюється за хешем: скасували все до збереженого стану — крапка зникає.

ревізії й id беруться з одного лічильника (`next_id` в індексі), тому ім'я знімка `<id>-<rev>.txt` ніколи не повторюється, навіть після перезапуску.

**номери рядків:** логічні рядки (абзаци rich edit), включно з переносом. без переносу — `EM_EXLINEFROMCHAR`; з переносом — tom, з кешем «позиція → рядок» для поточної ревізії (на прокрутці рахуються `\r` між сусідніми позиціями). ширина колонки — від кількості рядків, яку ryad рахує під час завантаження і після правок малих документів (`EM_GETLINECOUNT` перераховує макет).

**рядок статусу:** «ln N, col M» — рядок логічний, колонка в символах (code points) від початку логічного рядка; кодування; кінці рядків («mixed → crlf», якщо в файлі були різні); перенос.

## 6. протокол сесії

каталог `%LOCALAPPDATA%\ryad\` (або `--data` / `RYAD_DATA`):

```text
settings.ini            місце й стан вікна
crash.log               рядок на паніку: час і місце в коді, без тексту
session\session.ini     підтверджений індекс
session\session.bak     попередній індекс
session\<id>-<rev>.txt  знімки незбереженого тексту (utf-8, переноси як `\r`)
session\lock            відкритий ексклюзивно процесом-власником
```

**індекс** — текст `key = value`, перший рядок `ryad session 1` (версія формату), останній — `end = <fnv-64 усього, що вище>`. секції `[tab]` (відкриті вкладки по порядку), `[kept]` (чернетки, залишені з діалогу закриття), `[closed]` (чисті файлові вкладки для ctrl+shift+t). у записі: id, шлях, кодування, кінці рядків, версія файла на диску (розмір, час запису, fnv-64), знімок (ім'я, розмір, fnv-64), перенос, виділення, перший видимий символ, назва, час. імена знімків з індексу мають суворий вигляд `<цифри>-<цифри>.txt`, щоб пошкоджений індекс не вказав за межі каталогу.

**коли пишемо:** після правки — через 750 мс тиші, але не рідше ніж раз на 5 с безперервного набору; одразу — після закриття вкладки, «keep as draft», «discard», збереження файла; на виході й `WM_QUERYENDSESSION` — з очікуванням. знімок робиться тільки для документів зі змінами, і тільки якщо цієї ревізії ще нема в сесії.

**«keep as draft»** закриває вкладку тільки після того, як писальник підтвердив коміт з її знімком (`Writer::flush`). не вдалося — вкладка повертається на місце з текстом і undo, а користувач бачить причину.

**коміт (писальник):**
1. нові знімки: `<name>.tmp` → запис → `FlushFileBuffers` (`sync_all`) → `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)`;
2. індекс: `session.new` → запис → flush → `ReplaceFileW(session.ini, session.new, session.bak)` (перший раз — `MoveFileExW`);
3. прибирання: видаляються знімки, на які не посилаються ні новий індекс, ні `session.bak`, і залишки `.tmp`.

поки новий індекс не замінив старий, старий і всі його знімки цілі: переривання між кроками лишає попереднє покоління. перевірено тестами `session::tests` і запуском exe з `RYAD_TEST_FAULT=after-snapshots|after-index` (testing.md).

**порядок і застарілі задачі:** ui-потік віддає писальнику тільки готові коміти з наростаючим номером покоління. писальник виконує їх по черзі; коли їх набралося кілька, виконується найновіший індекс разом з усіма знімками, на які він посилається. старіший коміт не може перезаписати новіший.

**discard:** підтверджене «discard changes» додає id документа до `purge` наступного коміту, який іде одразу. id лишається в `purge` (і надсилається з кожним комітом), доки не вдасться коміт тієї генерації чи пізнішої. після заміни індексу писальник переписує й `session.bak` копією нового індексу і видаляє всі знімки цього id. отже жоден шлях відновлення (ні індекс, ні резервний індекс) не веде до відкинутого тексту, навіть якщо в черзі ще був старший автозапис.

**відновлення:** читаємо `session.ini`; пошкоджений (контрольна сума, формат) — `session.bak` з повідомленням. для кожного запису окремо:
- знімок є: читаємо й звіряємо розмір і хеш; не збігається — вкладка лишається з повідомленням «could not be fully restored», інші вкладки вантажаться;
- файлова вкладка зі знімком: якщо файл на диску змінився з того часу й **уже містить ці правки** (ctrl+s завершився, а коміт сесії — ні), вкладка чиста. інакше правки показуються як локальна копія з банером «the file changed on disk after these edits», а збереження пройде через діалог конфлікту. стара копія ніколи не відкривається «поверх» свіжішого файла без явної дії;
- чиста файлова вкладка читає файл; файла нема — вкладка з банером «not on disk anymore», «save as» / «open another»;
- перенос вмикається до завантаження тексту, а прокрутка (перший видимий символ) застосовується, коли вкладка вперше показана: rich edit прокручує до курсора, коли стає видимим і отримує фокус;
- чернетка без знімка — порожня.

**помилка запису сесії** під час роботи: банер червоним «unsaved text could not be written…» з «retry» і «save as…», автоповтор через 10 с; усі документи зі змінами будуть записані знову повністю. на виході — task dialog «retry / save as… / exit anyway», вікно лишається відкритим до вибору.

## 7. файли користувача

**читання:** розмір перевіряється до виділення буфера (межа 64 мб, `files::MAX_FILE_BYTES`). кодування: bom utf-8 / utf-16 le / utf-16 be; без bom — суворий utf-8; не utf-8 — питання «open as windows-1251» (а також «file › encoding › reopen as windows-1251»). utf-32 і непарний utf-16 не відкриваються. нулі — «схожий на бінарний». після завантаження текст у контролі порівнюється з декодованим (для файлів до 8 млн символів повністю, далі — за довжиною).

**кінці рядків:** запам'ятовується переважний стиль і чи були різні. ctrl+s на чистій вкладці, чий файл на диску не змінився, нічого не пише (перевірено: байти й час запису ті самі). після правок файл зі змішаними кінцями зберігається з переважним стилем, у статусі видно «mixed → crlf» ще до збереження. фінальний перенос — частина тексту, зберігається як є. bom зберігається разом з кодуванням.

**кодування при збереженні:** вихідне. символи, яких нема у windows-1251, — питання «save as utf-8» з першим таким символом і кількістю. «file › encoding» і «line endings» змінюють формат вкладки (вкладка стає зміненою).

**збереження (`files::save_atomic`):**
1. файл тільки для читання — помилка до будь-якого запису;
2. перед перезаписом той самий файл звіряється з версією, яку завантажили чи востаннє записали (розмір і час; якщо змінилися — хеш вмісту). змінився — діалог «save a copy… / reload from disk / overwrite / cancel». reload — заміна тексту одним кроком undo, тобто ctrl+z повертає правки;
3. тимчасовий файл поруч із ціллю `.<ім'я>.ryad-<pid>-<n>.tmp`, `create_new`, запис, `sync_all`, повторне читання й побайтове порівняння;
4. `ReplaceFileW(ціль, тимчасовий, …, REPLACEFILE_IGNORE_MERGE_ERRORS)` — зберігає атрибути, права й час створення цілі; для нового файла `MoveFileExW(WRITE_THROUGH)`;
5. будь-яка помилка: тимчасовий файл видаляється, ціль недоторкана, текст і прапорець змін у вкладці лишаються, діалог пропонує «save as…».

перевірено в `files::tests`: відсутня тека, файл тільки для читання, файл, відкритий іншим процесом без `FILE_SHARE_DELETE`, unicode-шлях без розширення, жодних залишків `.tmp`.

**той самий файл двічі:** шляхи порівнюються через `std::fs::canonicalize` (кінцевий шлях після посилань), без урахування регістру; відкриття вже відкритого файла переводить фокус на його вкладку. «save as» на файл, відкритий в іншій вкладці, відмовляє з поясненням.

## 8. провідник, другий запуск, drag and drop

- `ryad.exe <path> [path...]`: відносні шляхи розв'язуються в процесі, який викликали.
- другий запуск: `CreateMutexW(Local\ryad.<fnv каталогу даних>)` → вже існує → `FindWindowW(ryad.main.<fnv>)` → `AllowSetForegroundWindow` → `SendMessageTimeoutW(WM_COPYDATA, 5 с)`. власник відповідає 1 і відкриває шляхи вже після повернення (через `PostMessage`), щоб відправник не чекав на діалоги.
- вікна ще нема (власник стартує) — повтор кожні 50 мс до 10 с. власник закривається — відповідає 0, повтор; коли процес зникне, mutex зникає разом із ним, і новий запуск стає власником сам.
- власник тримає `session\lock` ексклюзивно, тож навіть за помилки з mutex другий процес не стане писати в той самий каталог сесії.
- drag and drop: на вікно (`WM_DROPFILES`) і на текст (`EN_DROPFILES` від rich edit — файли відкриваються, а не вставляються в текст).
- шляхи з провідника — тільки дані: жодних shell-команд з іменами файлів.

## 9. збірка

`panic = "abort"`: відновлення не покладається на штатний вихід. паніка закінчує процес так само, як «завершити процес»: лишається останній підтверджений коміт. панічний хук пише в `crash.log` час і місце в коді (без тексту). розміри профілів — measurements.md.

## 10. відомі обмеження (з коду й spike)

- emoji монохромні; у файлах понад 128k символів emoji з файла показуються квадратиками (текст цілий);
- vertical tab (`\v`) розриває рядок на екрані, але не є новим логічним рядком: без переносу номери рядків рахують його як рядок;
- смуга меню намальована ryad: екранний диктор не бачить її як смугу меню (самі меню — звичайні меню windows); рамка спливних меню — системна; смуги прокрутки — тема `DarkMode_Explorer` (документований `SetWindowTheme`, недокументована назва теми; невідома назва ігнорується);
- смуга вкладок малюється ryad і не видна екранному диктору як список вкладок; активна вкладка — у заголовку вікна, список — у меню «tabs»;
- ctrl+tab іде за порядком вкладок, а не за історією;
- файли користувача читаються й пишуться в ui-потоці: 50 мб — близько 4 с очікування з курсором «зачекайте».

## 11. markdown-предпросмотр

**запит користувача 2026-11-14:** предпросмотр markdown праворуч, у темі ryad і з акцентним кольором windows. бриф ставив markdown-preview поза 0.1; додано на прямий запит.

**компонент:** другий rich edit, у режимі rich text і `ES_READONLY` (`preview.rs`). webview не розглядали: він приніс би ~145 мб у 7 процесах (kadr measurements.md) заради однієї панелі. rich edit уже завантажений, вміє rtf-таблиці, заливку клітинок, рамки, шрифти й виділення з копіюванням.

**шлях:** текст активної вкладки (`EM_GETTEXTEX`) → `markdown::parse` (власна підмножина: заголовки atx/setext, абзаци й жорсткі переноси, жирний, курсив, закреслений, код, блоки коду, цитати, списки звичайні/нумеровані/задачі з вкладенням, таблиці з вирівнюванням, лінії, посилання, автопосилання, зображення як alt-текст, екранування) → `markdown::to_rtf` (7-бітний ascii, інші символи як `\uN?`) → `EM_SETTEXTEX`. власний парсер замість pulldown-cmark: потрібна тільки ця підмножина й одразу rtf; тести в `markdown::tests`.

**вигляд:** фон — `ground` теми (поле редактора — `raised`, тож панелі розрізняються), текст `ink`, маркери списків і цитати `ink2`, посилання й смужка цитати — акцентний колір. блоки коду й цитати — таблиці з однієї клітинки (заливка `\clcbpat` + `\clcfpat` + `\clshdng10000`; без `\clcfpat` заливка виходить чорною), таблиці — з рамками кольору `hair`, лінії під h1/h2 і `---` — порожній рядок таблиці з верхньою рамкою. сітку rich edit вимкнено (`SES_HIDEGRIDLINES`). розміри: тіло 15 px, h1 2×, h2 1.55×, міжрядковий 1.3.

**акцентний колір:** `HKCU\...\Explorer\Accent\AccentPalette` (8 відтінків, від найсвітлішого; сам акцент — №3). береться найближчий до акценту відтінок з контрастом ≥ 4.5:1 до фону: у темній темі світліші, у світлій — темніші. немає палітри — стандартні відтінки синього windows 11. зміна теми чи акценту (`WM_SETTINGCHANGE`, `WM_DWMCOLORIZATIONCOLORCHANGED`) перемальовує предпросмотр.

**коли:** файли `.md .markdown .mdown .mkd .mdwn` відкриваються з предпросмотром; `ctrl+shift+m` (view › markdown preview) вмикає й вимикає його для вкладки; стан вкладки — у сесії (`preview = 1`, старі індекси без цього рядка читаються як «вимкнено»). після набору — 250 мс тиші; перемикання вкладки, зміна розміру, теми чи dpi — одразу (якщо змінився ключ «документ, ревізія, ширина, кольори»). тексти понад 1 млн символів не показуються (повідомлення в панелі). прокрутка панелі йде за редактором пропорційно (частка прокрученого). роздільник перетягується (20–80 %, подвійний клік — навпіл), частка — у `settings.ini` (`preview_split`).

**знайдене:** у списках не можна ставити `\tx` на позицію відступу: msftedit 10.0.26100 рекурсивно падав із переповненням стека. з від'ємним `\fi` табуляція й так іде до `\li`. виміряно: зразкова нотатка (528 символів, усі елементи) — 42 мс від тексту до намальованої панелі.

## 12. смуга меню

смуга меню win32 у темній темі лишається світлою, і документованого способу це змінити немає. тому `menubar.rs` малює власний рядок «file edit view tabs» (gdi, кольори теми, наведення — `hover`, відкрите меню — `seg_on`). меню, що з нього відкриваються, — звичайні спливні меню win32 (`TrackPopupMenuEx`) з тим самим `HMENU`, тож `WM_INITMENUPOPUP` і `WM_COMMAND` не змінились.

- **owner-draw:** кожне спливне меню в `WM_INITMENUPOPUP` отримує фон теми (`SetMenuInfo`, `MIM_BACKGROUND`), а пункти — `MFT_OWNERDRAW` зі збереженим текстом. `WM_MEASUREITEM`/`WM_DRAWITEM` малюють пункт, гарячу клавішу праворуч (`ink3`), позначку ✓, неактивні пункти (`ink3`), роздільник (`hair`) і власну стрілку підменю (системну чорну обрізає `ExcludeClipRect`). мнемоніки owner-draw пунктів windows не бачить — їх знаходить `WM_MENUCHAR`. так само виглядають контекстне меню тексту й список вкладок.
- **клавіатура:** `alt` окремо, `f10` і `alt+f/e/v/t` відкривають меню (`App::menu_key` у циклі повідомлень, до акселераторів); ←/→ переходять між меню смуги, мишка над іншим пунктом смуги теж перемикає — через `WH_MSGFILTER` (`MSGF_MENU`) на час відкритого меню й `EndMenu`.
- **обмеження:** смуга не видна екранному диктору як смуга меню; рамка спливного меню — системна.

## 13. інсталятор у стилі kadr і заміна блокнота

вікно інсталятора — порт `installer.rs` kadr: заголовок, текст, піднята група з рядками-перемикачами, кнопка-пігулка; справжні кнопки windows, намальовані direct2d через `NM_CUSTOMDRAW`. те саме вікно показує видалення (`ryad --uninstall`). перемикачі: «replace windows notepad» (вимкнено за замовчуванням), «start ryad now» (увімкнено); у видаленні — «bring windows notepad back», якщо ryad його прибирав.

**заміна блокнота** — за зразком kadr і snipping tool: явна згода, запис про зміну, повернення при видаленні.
- `PackageManager::RemovePackageAsync` (winrt `Windows.Management.Deployment`) для пакетів сімейства `Microsoft.WindowsNotepad_8wekyb3d8bbwe` поточного користувача — без прав адміністратора; позначка `HKCU\Software\ryad\Setup\notepad_removed`;
- потім `ms-settings:defaultapps?registeredAppUser=ryad`: сторінка ryad у «типових програмах» (windows 11 з оновленням 2023-04 і новіші; старіші — загальна сторінка). windows вимагає, щоб типові програми задавав користувач у системному інтерфейсі (learn.microsoft.com, «launch the default apps settings page»), тож ryad сам типовим себе не робить;
- старий `notepad.exe` (необов'язковий компонент «notepad (system)») потребує прав адміністратора — ryad його не чіпає;
- при видаленні з увімкненим «bring windows notepad back» відкривається сторінка блокнота в microsoft store (`ms-windows-store://pdp/?ProductId=9MSMLRH6LZF3`), позначка прибирається;
- у пісочниці тестів (`RYAD_TEST_SANDBOX`) пакет не чіпається й нічого не відкривається: пишеться тільки позначка.

**залежності:** додано `windows-numerics` 0.3.1 (той самий репозиторій microsoft/windows-rs, що й `windows`; матриці для direct2d) і features `Win32_Graphics_Direct2D*`, `Win32_Graphics_DirectWrite`, `Win32_Graphics_Dxgi_Common`, `Management_Deployment`, `ApplicationModel`, `Foundation*`. exe: 504 → 613 кб.
